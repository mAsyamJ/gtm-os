# V5 publishing and GTM architecture

Revision: v5-r1. Audience: maintainers/operators. Input authority: owner V5 prompt, approved implementation plan, tenant governance and individually reviewed evidence. Approval: local engineering authorized; publication pending exact owner action. Source/license: original project code, existing MIT dependencies, separately attributed documentation; initial live slice is text-only.

`packages/v5` extends the compiled CLI ahead of V3 dispatch. V3/V4 stores, native-only packet hashes, decisions, claims and historical receipts remain unchanged. Existing disabled-write configuration is preserved. V5 is an explicitly scoped approval-controlled capability, not a global switch enabling old publisher routes.

`PublisherAdapter` exposes discovery, probe, schedule, queued/sent reads, metrics, reconciliation and cancellation. Buffer is the only implemented live provider. It uses GraphQL variables at `https://api.buffer.com`, Bearer service credentials, organization discovery, exact `service: twitter`, handle/service ID checks, queue/disconnection/lock and scheduling permissions. HTTP status is insufficient: GraphQL errors and mutation unions are separately checked. [Buffer contracts](https://developers.buffer.com/reference), [scheduling](https://developers.buffer.com/examples/create-scheduled-post.html).

Observed and synthetic publishing databases are physically separate under each tenant's state directory. New tables hold channels, text packets, jobs, immutable owner decisions, attempts, provider receipts, metric snapshots and hash-chained outbox events. Jobs are mutable projections checked against immutable audit state. SQLite WAL/FULL, immediate transactions, unique content/channel/time and provider IDs, file permissions, safe workspace paths and link rejection follow existing storage patterns. A shared administrative budget database prevents account-key rotation or tenant switching from resetting the local free-plan ceiling. It contains request reservations and quota headers, never copy or credentials.

Lifecycle: `DRAFT → REVIEWED → APPROVAL_PENDING → APPROVED → SUBMITTING → SCHEDULED → SENT → MEASURED`. HOLD, FAILED, CANCELLED, RECONCILE_REQUIRED and EXTERNAL_URL_PENDING remain distinct. A job claim and channel lease serialize local workers before preflight calls. Submission intent is durable before mutation. Expired in-flight leases, crashes, uncertain responses and schema failures require reconciliation, never automatic resend. Recovery uses exact remote ID, or a complete bounded queued/sent search matching channel, text, media absence and time. Zero/multiple matches remain unresolved. Manual additions can still race a remote queue read; provider errors remain authoritative.

Approval binds exact canonical text, tenant, account, Buffer principal/organization/channel/service identity, content/governance/source/review/media hashes, UTC time, audience zone and zero provider-cost cap. Local owner approval records are attestations backed by a genuine owner confirmation reference; hashes provide integrity, not a claim of digital signer authentication. They must never be generated by an agent as if owner review occurred. A changed payload, elapsed slot, stale source or revoked approval cannot authorize a new submission. Legacy approvals never authorize Buffer. Cancellation needs an exact separate owner decision and a currently scheduled remote post.

Default scheduling/refill/cancel is local dry-run. Explicit `--execute` is required. Unsupported providers/media return UNSUPPORTED. Text-only payloads do not inherit V4's mandatory video/image packaging; media schema still verifies rights, scope and hashes before any future support. No media host/upload authority is inferred.

Budgets are initially 90 requests/15 minutes, 90/day and 2,700/30 days, including failed reservations. Structured RateLimit/RateLimit-Policy headers tighten remaining budgets; exhausted windows defer work by returning a blocker. There is no sleeping retry loop or automatic mutation retry. Queue target is at most eight pending posts/channel. [Limits](https://developers.buffer.com/guides/api-limits.html), [Free plan](https://buffer.com/pricing).

The seven-day calendar follows the owner's five-post weekly cadence for both accounts in America/New_York, with UTC persistence and WIB display. A fresh observed Buffer schedule supplies its actual slots; mismatches block the calendar. Without fresh discovery, weekday 09:00 times are proposals. DST ambiguity/nonexistence is rejected. Buffer handles future publishing; invocation of the local refill/reconcile commands is the operator's responsibility. A per-tenant systemd template is supplied but not installed. No timer or second publishing provider is activated.

Founder 5+5 accepts five exact reviewed source statements from authorized activity/owner inputs, or emits missing slots, then five prioritized suggestions. GitHub/Beads statements must be ingested/reviewed through the existing evidence boundary; the loop never infers a personal achievement or production shipment from a commit. Research queues accept bounded evidence-linked candidate files, while raw seed suggestions and search-discovered X URLs remain discovery-only. No reply or DM worker exists.

Buffer metrics retain provider origin and refresh clocks. Authorized UTM product exports remain owner-attested, deduplicated observations. All four UTM values must match one exact link in the approved post; choose an opaque tracking value before hashing the payload, since embedding a payload's own hash in its text URL is circular. Text-only questions without a UTM link cannot support a per-post product attribution claim. Weekly learning keeps UNKNOWN distinct from measured zero, preserves legacy scorecards and does not invent platform/product verification or causal growth. Product-side instrumentation outside this repository needs separate authorization.

Validation: `pnpm check`, `python3 scripts/verify_v5.py`. Live capability is only established by genuine provider/public receipts; deterministic fixtures remain SYNTHETIC. Initial acceptance requires exactly one distinct post per tenant and independent public proof.
